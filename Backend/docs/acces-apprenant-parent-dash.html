Accès Apprenant ↔ Parent — schéma dash

Adaptation du système d'accès validé côté bet-elearning (acces-apprenant-parent-bet-elearning.html) au modèle de données réel de dash : deux canaux d'inscription distincts, des champs enfant séparés au lieu d'un nom_complet unique, et un lien parent qui passe par assignations_parcours plutôt que classes_elearning_apprenants.

dash + Backend (tables classiques, hors e-learning) 2 canaux d'inscription Rien de ce système n'existe encore côté accès — à construire
🔀 Différence structurante avec bet-elearning : dash ne convertit pas toujours l'inscription enfant en une seule écriture. Le formulaire web ("j'inscris mon enfant") écrit dans une table de leads brute (inscriptions_enfants), tandis que la commerciale, elle, écrit directement dans la table pivot assignations_parcours — avec, en plus, des champs enfant séparés (prenom_enfant, nom_enfant, age_enfant, niveau_classe_enfant) là où bet-elearning n'a qu'un nom_complet à découper côté frontend.

Deux canaux d'inscription, une seule finalité

Contrairement à bet-elearning (un seul flux d'inscription, converti directement en ligne classes_elearning_apprenants), dash a deux points d'entrée qui ne se rejoignent pas automatiquement.

Modèle de champs — bet-elearning vs dash

🟣 bet-elearning — classes_elearning_apprenants
  • nom_complet — un seul champ, split côté frontend par .split(' ') pour dériver prénom/nom.
  • date_naissance — pilote directement calcTranche() (≤12 enfant, ≤17 ado, sinon adulte).
  • profil_type — stocké mais lu uniquement côté backend (calcul estParent).
  • email_parent / telephone_parent — clé de jointure parent→enfant.
🟢 dash — assignations_parcours / inscriptions_enfants
  • prenom_enfant + nom_enfant — champs séparés dès la saisie, pas de split à faire.
  • age_enfant — âge saisi directement par la commerciale (pas de date_naissance systématique sur ce formulaire) ; inscriptions_enfants a en plus date_naissance et tranche_age.
  • niveau_classe_enfant — spécifique dash, sans équivalent côté bet-elearning (niveau scolaire, pas niveau CECR).
  • profil_type — même usage prévu (adulte/étudiant/enfant), déjà présent nativement.
  • nom_parent / email_parent / telephone_parent — mêmes clés de jointure, mais vers assignations_parcours et non classes_elearning_apprenants.

Pièges bet-elearning à ne pas reproduire dans dash

✕
Flag estParent calculé mais jamais lu
Côté bet-elearning, ce flag existe côté backend mais n'est utilisé dans aucune branche du login standard. Pour dash, le brancher réellement dès la première version évite de recréer ce trou.
✕
2FA parent mocké
Code fixe côté bet-elearning — à faire correctement dès le départ pour dash si un vrai 2FA est nécessaire, ou à ne pas afficher du tout plutôt que simuler une sécurité qui n'existe pas.
✕
Résolution des enfants sans API dédiée (dépendance RLS)
bet-elearning interroge Supabase directement depuis le frontend. Pour dash, préférer un endpoint backend explicite (comme le reste des routes mon-espace/apprenants), plus facile à tester et à sécuriser.
✓
Comptes Auth séparés parent/enfant
Pattern à reprendre tel quel : un compte Supabase distinct par parent, lié uniquement par email_parent — pas de FK rigide, cohérent avec ce que dash fait déjà pour d'autres liaisons (ex. groupes.js).
✓
Résolution téléphone → email de connexion
Le pattern resolve-phone-parent est directement réutilisable en pointant vers assignations_parcours.telephone_parent au lieu de classes_elearning_apprenants.
