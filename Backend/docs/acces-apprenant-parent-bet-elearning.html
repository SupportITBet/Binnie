bet-elearning · Référence technique — à porter ailleurs

Accès Apprenant ↔ Parent — schéma complet

Comment un apprenant se connecte, comment son dashboard s'adapte selon son profil (enfant / adolescent / adulte), comment un parent est créé, se connecte et retrouve ses enfants. Document de référence pour porter ce système ailleurs — chaque étape cite le fichier et les lignes exactes.

bet-elearning + Backend Lecture seule — aucun code modifié 8 étapes · 2 comptes Auth · 1 divergence clé
🔑 Point le plus important à retenir avant de porter ce système ailleurs : le profil affiché (enfant/ado/adulte) n'est jamais lu depuis la colonne stockée profil_type — il est recalculé côté client à chaque chargement à partir de date_naissance. Le champ stocké ne sert qu'au backend, pour un calcul différent (détecter qu'un parent se connecte avec son propre email faute d'email enfant). Reproduire ce système ailleurs oblige à choisir explicitement lequel des deux mécanismes on réplique.

Le flux, de bout en bout

Huit étapes, de l'inscription à l'affichage du dashboard parent avec plusieurs enfants.

1
Inscription
La ligne apprenant est créée avec tout le contexte parent
À l'assignation de classe (PATCH /api/inscriptions-elearning/:id/assigner, Backend/src/routes/inscriptionsElearning.js:508-524), une ligne complète est insérée dans classes_elearning_apprenants : identité de l'apprenant (nom_complet, email, date_naissance), niveau CECR, et coordonnées parent (nom_parent, email_parent, telephone_parent) + profil_type.
Onboardingclasses_elearning_apprenants
2
Connexion apprenant
Auth Supabase directe, puis vérification d'éligibilité
LoginApprenant.jsx délègue tout à AuthContext.seConnecter() (bet-elearning/src/contexts/AuthContext.jsx:277-363) : supabase.auth.signInWithPassword() puis appel à GET /api/apprenants/check-eligibilite avec le token. Le rôle stocké (bet_profil_mock.role) vient uniquement de app_metadata.role du JWT Supabase — jamais du flag estParent renvoyé par cet endpoint.
const roleJWT = appMeta.role || userMeta.role; const estParent = roleJWT === 'parent'; // check.estParent (renvoyé par le backend) n'est PAS lu ici role: estParent ? 'parent' : 'apprenant'
Apprenantcheck-eligibilite
Un enfant sans email propre (connecté avec l'email de son parent) reste traité comme "apprenant" ici — le cas n'est géré que dans le chemin parent par téléphone (étape 6).
3
Dashboard apprenant
L'UI se recalcule depuis la date de naissance, pas depuis profil_type
DashboardApprenant.jsx:888-908 relit la ligne classes_elearning_apprenants puis calcule tranche_age = calcTranche(date_naissance) (utils/trancheAge.js : ≤12 → enfant, ≤17 → adolescent, sinon adulte). Le hook useAgeInterface(apprenant) (hooks/useAgeInterface.js, appelé ligne 988) dérive ensuite couleurs, wording et visibilité de blocs entiers (voir tableau ci-dessous).
ApprenantcalcTranche · useAgeInterface
4
Création de l'accès parent
100% manuelle, déclenchée par l'onboarding — jamais par le parent
POST /api/apprenants/creer-acces-parent (Backend/src/routes/apprenants.js:687-805, authenticateAdmin) : crée un compte Supabase Auth séparé avec app_metadata.role = "parent", upsert la ligne utilisateurs correspondante, puis lie systématiquement email_parent sur la ligne classes_elearning_apprenants de l'enfant. Aucun email/SMS de bienvenue n'est envoyé automatiquement à cette étape (contrairement à la création d'accès apprenant).
OnboardingSupabase Auth · utilisateurs
Aucun endpoint "demande d'accès parent" n'existe côté parent — pas d'auto-inscription possible.
5
Connexion parent — par email
Même chemin que l'apprenant, rôle porté par le JWT
LoginParent.jsx en mode email appelle le même seConnecter() que l'apprenant. C'est uniquement parce que app_metadata.role = "parent" a été posé à l'étape 4 que roleJWT === 'parent' et que la redirection finit sur /parent/dashboard (ROLE_REDIRECT.parent, constants/roles.js:74).

6
Connexion parent — par téléphone
Résolution du numéro vers un email, puis connexion forcée "parent"
LoginParent.jsx en mode téléphone appelle POST /api/apprenants/resolve-phone-parent (apprenants.js:46-83) : normalise le numéro, cherche une correspondance dans classes_elearning_apprenants.telephone_parent (comparaison en mémoire côté Node, pas de filtre SQL), renvoie email_parent || email. La connexion utilise ensuite seConnecterParent() — qui force role: 'parent' directement, sans repasser par check-eligibilite.
Parentresolve-phone-parent
C'est le seul chemin où le cas "enfant sans email propre" est traité correctement de bout en bout.
7
2FA
Simulé, pas une vraie sécurité
LoginParent.jsx propose une étape 2FA, mais AuthContext.valider2FA() compare simplement à un code fixe en dur (123456). Le flux Manager BET, lui, utilise supabase.auth.mfa réel — ce n'est pas le cas ici.

À ne pas reproduire tel quel si le portage doit être en production.
8
Dashboard parent
Résolution des enfants en direct via Supabase, pas via une API dédiée
DashboardParent.jsx:90-145 interroge directement supabase.from('classes_elearning_apprenants').eq('email_parent', profile.email) — c'est la seule clé de jointure parent→enfants, il n'y a pas de colonne parent_id. Le sélecteur multi-enfants (lignes 55-56, 332-344) n'apparaît que si plusieurs lignes remontent ; changer d'enfant actif recharge présences, résultats, devoirs, séances et contenus pour cet enfant précis.

Stocké en base vs réellement utilisé

Le champ profil_type existe, est renseigné à l'inscription, mais son usage réel est plus étroit qu'on ne l'attendrait.

📦 Stocké — profil_type
  • Colonne classes_elearning_apprenants.profil_type — valeurs enfant / adolescent / adulte (défaut adulte).
  • Renseignée à l'inscription, propagée à l'assignation de classe.
  • Lue uniquement côté backend, dans check-eligibilite, pour calculer estParent.
  • Jamais lue par DashboardApprenant.jsx (0 occurrence confirmée).
⚙️ Réellement utilisé — date_naissance
  • calcTranche(date_naissance) recalculée côté client à chaque chargement (dashboard ET AuthContext.chargerProfil()).
  • ≤ 12 ans → enfant, ≤ 17 ans → adolescent, sinon → adulte.
  • Pilote tout ce qui est listé dans le tableau ci-dessus (wording, blocs, mini-jeux, menu).
  • Si date_naissance est absente ou invalide → repli silencieux sur adulte.

Colonnes clés de classes_elearning_apprenants

apprenant_idFK vers utilisateurs — compte réel de l'apprenant, clé de lecture du dashboard.
emailEmail de connexion de l'apprenant — peut être virtuel (tel.xxx@betacademy.app) si pas d'email réel.
date_naissancePilote l'adaptation UI via calcTranche() — pas profil_type.
nom_completPas de colonnes séparées prénom/nom — le split se fait côté frontend par .split(' ').
profil_typeStocké mais lu uniquement côté backend (check-eligibilite) pour le calcul estParent.
email_parentClé de jointure parent→enfants — utilisée par DashboardParent.jsx, resolve-phone-parent, creer-acces-parent. Aucune colonne parent_id rigide.
telephone_parentClé de résolution dans resolve-phone-parent (comparaison en mémoire, pas de filtre SQL indexé).
statutFiltré partout via .neq('statut', 'suspendu').

Pièges relevés — à ne pas reproduire tel quel

✕
estParent calculé mais jamais lu
Le flag renvoyé par check-eligibilite n'est utilisé dans aucune branche de seConnecter() — un enfant sans email propre reste "apprenant" tant qu'il ne passe pas par le login parent/téléphone.
✕
2FA parent mocké
Code fixe 123456 côté AuthContext.valider2FA — aucune vraie vérification, contrairement au flux Manager BET (supabase.auth.mfa réel).
✕
Pas d'auto-demande d'accès parent
Seul un compte admin (onboarding) peut créer un accès parent — aucun endpoint self-service côté parent.
✕
Résolution des enfants sans API dédiée
DashboardParent interroge Supabase directement (RLS) — dépendance à des règles non auditées ici, pas d'endpoint backend testable isolément.
✓
Comptes Auth séparés dans le cas standard
Parent et enfant ont chacun leur compte Supabase Auth, liés uniquement par email_parent — pas de FK rigide, facile à porter.
✓
resolve-phone-parent + creer-acces-parent forment un flux complet
Couvre correctement le cas "enfant sans email propre" de bout en bout, contrairement au chemin email standard.
