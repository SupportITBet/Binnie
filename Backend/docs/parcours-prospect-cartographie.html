Deux mécanismes de transfert vers le PA Advisor
① Pool partagé — coaching privé confirmé

À la finalisation, si l'offre est du coaching privé, aucun PA n'est désigné à l'affichage (le prospect/parent voit juste "vous serez contacté par un PA Advisor") — tous les PA actifs sont notifiés, et n'importe lequel peut prendre le dossier en charge lui-même.

Déclenché parSans assistante pré-désignée (isDirectCommerciale && type_coaching==="prive") dans POST /parcours/assignation
ÉcritnotifyRole("pedagogical_advisor") à la création — puis PATCH /assignations/:id → pa_advisor_id quand un PA clique "🙋 Prendre en charge" depuis Prospects parcours
DestinationVisible de tous les PA dans Prospects parcours jusqu'à prise en charge ; une fois pa_advisor_id posé (au clic "Converti"), bascule dans Mes apprenants du PA qui l'a pris
② Signalement automatique — canal croisé

Construit récemment : si un prospect obtient une seconde assistante sur un canal différent de sa première assignation, le serveur alerte les PA sans jamais bloquer la nouvelle demande.

Déclenché parPOST /parcours/assignation, détection automatique côté serveur
ÉcritNotification notifyRole("pedagogical_advisor") avec meta.assignation_id
Destination● PA Advisor → onglet Dossiers à réaffecter, résolution via PATCH assistante_id

Les deux clés de routage stable

routing_statut n'est qu'un indicateur d'étape ; ce sont ces deux champs qui filtrent réellement l'accès
pa_advisor_id Posé quand un PA clique "Prendre en charge" (pool ①) ou au moment du "Converti". Lu par GET /mes-apprenants-pa, filtré strictement égal à l'ID du PA connecté — c'est la seule vraie porte d'entrée de l'onglet "Mes apprenants" du PA.
onboarding_id Figé dès la création de l'assignation, recopié depuis la fiche de l'assistante assignée. Peut être réécrit plus tard par le commercial ou le PA. Lu par mes-apprenants-onboarding avec un triple repli (assistante → JSON de secours → filtrage mémoire) si la donnée est absente.

États de routing_statut

Une machine à états UI — ne restreint l'accès SQL que pour l'onboarding
centre_assigne Posé par le commercial (présentiel) après affectation à une classe — bascule l'UI vers "prêt à transmettre".
pa_en_attente Posé automatiquement dès la création si aucune assistante n'est pré-désignée (pool ①). Rend le dossier visible dans les badges du PA — pas de filtre SQL dédié, c'est pa_advisor_id qui fait le vrai filtrage.
pa_affecte Posé par le PA une fois un coach affecté au dossier. Étape intermédiaire avant transmission à l'onboarding.
onboarding_en_attente Le seul état avec un vrai filtre SQL (eq strict). Alimente directement ● OnboardingDashboard → Nouveaux apprenants. Déclenche désormais une notification (notifyUser si onboarding_id connu, sinon notifyRole("onboarding")) — jusqu'ici l'onboarding ne découvrait un dossier transmis qu'en rafraîchissant sa liste par hasard.
onboarding_affecte Posé par l'onboarding une fois la classe créée et l'apprenant réellement inscrit dans groupes_apprenants (confirmerAffectation). Déclenche une notification au pa_advisor_id du dossier — même trou que ci-dessus, corrigé côté PATCH /assignations/:id.

Le piège identité enfant ↔ parent

Root cause récurrente de nombreux bugs de dossiers "orphelins"

Pour un profil_type:"enfant", prospect_email/prospect_telephone sur assignations_parcours sont ceux du parent (c'est lui qui remplit le formulaire) — jamais ceux de l'enfant. Tout code qui retrouve un dossier par correspondance d'email/téléphone entre assignations_parcours.prospect_email et groupes_apprenants.email_apprenant (l'identifiant technique réel de connexion de l'enfant, généré <nom>@betacademy.app ou tel.<numéro>.<nom>@betacademy.app) échoue systématiquement pour ce cas — ces deux valeurs ne sont jamais égales.

Symptômes observésInfos parent absentes du profil, paiement/présences/séances introuvables, "Aucun compte créé" alors que l'accès existe, test de niveau du parent recopié sur le dossier de l'enfant (et vice-versa), classes invisibles dans "Mes classes" côté commerciale/PA.
Lien fiablegroupes_apprenants.note (JSON) contient assignation_id, posé une seule fois à la création de la classe (confirmerAffectation / "Assigner classe & coach"). C'est la seule clé qui doit servir à relier les deux tables pour un profil enfant — jamais l'email.
Corrigé (partout où trouvé)Onboarding/Commercial/PA : modals détail apprenant, onglets Accès/Parent/Présences/Paiements/Séances, filtrage des classes par assistante (GET /api/groupes), auto-remplissage du niveau (level-test/submit via assignation_id explicite plutôt qu'un matching par email).
Prévention à la créationemail_apprenant/telephone ne sont plus jamais pré-remplis avec les coordonnées du parent pour un profil enfant (laissés vides → identifiant technique généré), pour ne pas "occuper" ces coordonnées et bloquer la création d'un compte parent séparé.

Table seances unifiée

Remplace progressivement groupes_cours, seances_privees et sessions_live

Les coachs enregistrent désormais leurs séances (groupe et privé) dans une table unique seances (colonne circuit : groupe/prive/live, liée par groupe_id), qui alimente aussi le calcul des honoraires. Les anciennes tables (groupes_cours, seances_privees, sessions_live) restent lues en repli pour les données historiques, mais toute vue (Onboarding, PA, apprenant, parent) doit interroger seances par groupe_id en priorité — sinon des séances bien réelles (et comptées dans les honoraires du coach) n'apparaissent nulle part côté suivi pédagogique.
